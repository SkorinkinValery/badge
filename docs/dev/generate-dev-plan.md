# Задача: декомпозировать docs/PLAN.md в пошаговый план разработки (TDD)

Ты — техлид MVP «Аудиобейдж». Твоя задача — **только спланировать**, не писать production-код.
Преврати высокоуровневый `docs/PLAN.md` в подробный, последовательный, исполнимый план разработки,
где **каждый пункт — самодостаточное задание** для разработчика или кодинг-агента, а крупные шаги
разбиты на простые. Весь процесс строится по **TDD**.

## Что прочитать (источники истины — не противоречить им)

1. `docs/PLAN.md` — стек, архитектура ports & adapters, этапы M0–M10, модель данных, verification, риски.
2. `docs/TZ-audiobadge-mvp.md` — требования заказчика (scope, KPI, функц. блоки, юр-момент ПДн).

Прочитай оба файла целиком до начала работы. Если docs/PLAN.md и ТЗ расходятся — приоритет у docs/PLAN.md
(в нём зафиксированы технологические решения), но отметь расхождение в индексе.

## Что произвести (формат вывода)

Создай **только** файлы внутри `docs/dev/tasks/`. Язык — **русский**. Markdown.

- **Индекс** `docs/dev/tasks/README.md`:
  - список всех этапов M0–M10 в порядке выполнения, со связями (что что разблокирует) и пометкой,
    какие этапы можно вести параллельно;
  - глобальные соглашения: TDD-цикл, слои тестов, общий Definition of Done, инструменты
    (pytest, httpx, mypy, ruff/lint, jiwer для WER), запуск тестов в CI;
  - сквозные инварианты архитектуры (см. ниже).
- **По одному файлу на этап** (шард), напр.:
  `M0-skeleton.md`, `M1-core-ports-graph.md`, `M2-filesource-upload.md`, `M3-stt-whisper.md`,
  `M4-analyzer-scoring.md`, `M5-auth-ui.md`, `M6-admin.md`, `M7-micsource-realtime.md`,
  `M8-export-sheets.md`, `M9-selfhost-llm-fallback.md`, `M10-data-metrics.md`.

В начале каждого шарда — краткая цель этапа, входные предпосылки (что должно быть готово),
выходной результат (DoD этапа) и чек-лист задач этапа.

## Декомпозиция: правила

- Каждый этап M* разбей на **упорядоченные задачи** с ID вида `M2-T1`, `M2-T2`, …
- Размер задачи — на **одну сфокусированную сессию / один PR**. Если задача больше — дроби дальше
  на подшаги (red/green-итерации). Лучше много мелких, чем несколько крупных.
- Явно указывай **зависимости** между задачами и между этапами.
- Каждая задача оформляется строго по шаблону ниже.

## TDD — обязателен для каждой задачи

Каждая задача (кроме чисто конфигурационных) идёт циклом **red → green → refactor**:
1. **Red** — сначала написать падающий тест(ы): перечисли конкретные тест-файлы и кейсы.
2. **Green** — минимальная реализация, делающая тест зелёным.
3. **Refactor** — чистка без изменения поведения; тесты остаются зелёными.

Для каждой задачи укажи **слой тестов** (могут сочетаться):
- **Контракт-тесты портов** (`AudioSource`/`STTEngine`/`Analyzer`/`CRMExporter`) — один набор
  тестов на порт, прогоняется против fake-/стаб-адаптеров и реальных реализаций.
- **Unit** — чистые функции (скоринг `kpi_json + weights → score/verdict`, нормализация весов,
  парсинг конфигов).
- **Интеграционные** — прогон LangGraph-графа со стаб-STT/LLM, проверка переходов статусов и ветки
  `failed`, персист состояния через checkpointer.
- **API** — FastAPI-роутеры через httpx/pytest (upload, recordings, auth, admin, ws_mic).
- **Eval-скрипты** (`eval_wer.py`, `eval_kpi.py`, regression-харнесс) — как **некритичные**
  quality-gate на размеченном наборе, не блокируют CI на пустом датасете.

Правила: ничего не «мёржится» красным; CI гоняет lint + mypy + tests; покрытие критичной логики
(скоринг, порты, граф) — тестами в первую очередь.

## Сквозные инварианты архитектуры (проверять в каждой задаче)

- **Ports & adapters**: ядро не зависит от реализаций; провайдеры за портами.
- **Сменность только конфигом**: LLM/STT/CRM меняются через `base_url`/`model`/`api_key`/выбор
  адаптера — без правок кода. Дефолты MVP: faster-whisper, `gpt-4o-mini`, `GoogleSheetsExporter`,
  оркестрация — LangGraph, checkpointer — Postgres.
- **Config-driven**: KPI/веса/провайдеры/язык — из `kpi.yaml`/`weights.yaml`/`providers`, не хардкод.
- **Стабы перспективы**: `BadgeSource`/`TelephonySource` — заглушки, не ломающие ядро.
- **Self-host LLM (vLLM/Qwen)** — целевой шаг после MVP, подключается тем же портом сменой конфига.
- **ПДн**: `consent_flag`, ограничение доступа по роли, `retention_until`/джоба удаления — где релевантно.

## Шаблон одной задачи (использовать дословно)

```markdown
### M{N}-T{k}: <короткое название>

- **Цель / зачем:** <1–2 предложения, какую ценность даёт>
- **Зависит от:** <ID задач или «нет»>
- **Затрагивает:** <модули/файлы по структуре из docs/PLAN.md §2.2>
- **TDD:**
  1. *Red* — тесты: `<путь к тест-файлу>` — кейсы: <перечислить>
  2. *Green* — реализация: <что минимально написать>
  3. *Refactor* — <что вычистить>
- **Слой тестов:** <контракт | unit | интеграция | API | eval>
- **Definition of Done:** <чёткие критерии: тесты зелёные, mypy/lint ок, конфиг-driven, лог/ошибки и т.п.>
- **Acceptance / как проверить:** <команда/сценарий ручной проверки, если применимо>
- **Заметки по портам/конфигу:** <как сохраняется сменность провайдера>
```

## Глобальный Definition of Done (вынеси в индекс, ссылайся из задач)

- Тесты зелёные (unit/контракт/интеграция/API по релевантности); CI проходит.
- `ruff`/lint и `mypy` без ошибок на новом коде.
- Никакого хардкода провайдеров/KPI/весов — всё из конфига.
- Структурные логи и обработка ошибок/retry в стадиях графа.
- Где есть боевые записи — учтены `consent_flag` и `retention`.
- Обновлена релевантная документация/ADR при изменении решения.

## Чего НЕ делать

- Не писать production-код и не скаффолдить репозиторий — **только план в `docs/dev/tasks/`**.
- Не менять `docs/PLAN.md`, `docs/TZ-audiobadge-mvp.md` и другие существующие файлы.
- Не задавать уточняющих вопросов — выдай полный план; спорные места помечай как «открытый вопрос»
  в индексе.

## Критерий готовности твоей работы

Есть `docs/dev/tasks/README.md` + по одному шарду на каждый этап M0–M10; в каждом шарде задачи
оформлены по шаблону, у каждой задачи прописан TDD-цикл и слой тестов; сохранены сквозные
инварианты архитектуры; порядок и зависимости этапов явны.
