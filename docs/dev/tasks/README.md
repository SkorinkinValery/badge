Этапы превращают высокоуровневые M0–M10 из `docs/PLAN.md §5` в упорядоченные задачи `M{N}-T{k}`.
Каждая задача = один сфокусированный PR / одна сессия.

  M4 ──► M5 (auth + UI карточка) ──► M6 (админка: менеджеры/скрипты/сводка)
  M4 ──► M7 (MicSource near-realtime)        # параллельно M5/M6 после M3+M4

Фаза C (интеграции и качество)
  M4 ──► M8 (экспорт: GoogleSheets → webhook → bitrix24)   # параллельно M5–M7

## 2. Глобальные соглашения (TDD, тесты, инструменты)

### 2.1 TDD-цикл (обязателен для каждой задачи, кроме чисто конфигурационных)

1. **Red** — сначала пишем падающий тест(ы): конкретные тест-файлы и кейсы перечислены в каждой задаче.
2. **Green** — минимальная реализация, делающая тест зелёным.
3. **Refactor** — чистка без изменения поведения; тесты остаются зелёными.

Правила: **ничего не мёржится красным**; CI гоняет `lint + mypy + tests`; покрытие критичной логики
(скоринг, порты, граф) — тестами в первую очередь.

### 2.2 Слои тестов

- **Контракт-тесты портов** (`AudioSource` / `STTEngine` / `Analyzer` / `CRMExporter`) — **один**
  параметризованный набор на порт; прогоняется против fake-/стаб-адаптеров и реальных реализаций.
  Реализация порта обязана пройти его «как есть».
- **Unit** — чистые функции: скоринг (`kpi_json + weights → score/verdict`), нормализация весов,
  парсинг `kpi.yaml`/`weights.yaml`/`providers`, валидация Pydantic-схем.
- **Интеграционные** — прогон LangGraph-графа со стаб-STT/LLM: переходы статусов
  `normalizing→transcribing→analyzing→scoring→exporting`, ветка `failed` (стадия+ошибка+retry),
  персист состояния через checkpointer (Postgres).
- **API** — FastAPI-роутеры через `httpx`/`pytest` (`uploads`, `recordings`, `auth`, `managers`,
  `scripts`, `admin`, `ws_mic`).
- **Eval-скрипты** (`scripts/eval_wer.py`, `scripts/eval_kpi.py`, `scripts/regression_harness.py`) —
  **некритичный** quality-gate на размеченном наборе; **не блокируют CI на пустом датасете**
  (skip/xfail при отсутствии `datasets/`).

### 2.3 Инструменты

| Назначение | Инструмент |
|-----------|-----------|
| Тест-раннер | `pytest` (+ `pytest-asyncio` для async) |
| HTTP-тесты API | `httpx` (ASGI transport) |
| Типизация | `mypy` (strict на новом коде) |
| Линт/формат | `ruff` (lint + format) |
| WER | `jiwer` |
| Схемы/валидация | `pydantic` v2 (structured/JSON output, `response_format`) |
| Миграции | `alembic` |
| ORM | `SQLAlchemy 2.0` |
| Оркестрация | `LangGraph` (checkpointer — Postgres) |
| Контейнеры в тестах БД | `testcontainers` / dockerized postgres+minio (по выбору этапа) |

### 2.4 CI

CI на каждый PR: `ruff check` → `ruff format --check` → `mypy` → `pytest` (unit + контракт + интеграция + API).
Eval-скрипты — отдельная **некритичная** джоба (`continue-on-error`), запускается только при наличии `datasets/`.

## 3. Глобальный Definition of Done (ссылаться из каждой задачи)

Задача считается готовой, когда:

- ✅ Тесты зелёные (unit/контракт/интеграция/API по релевантности); CI проходит.
- ✅ `ruff` (lint + format) и `mypy` без ошибок на новом коде.
- ✅ Никакого хардкода провайдеров/KPI/весов — всё из конфига (`kpi.yaml`/`weights.yaml`/`providers`).
- ✅ Структурные логи и обработка ошибок/retry в стадиях графа (где применимо).
- ✅ Где есть боевые записи — учтены `consent_flag` и `retention` (`retention_until` + джоба удаления).
- ✅ Обновлена релевантная документация/ADR при изменении решения.

В шардах из задач этот блок упоминается как «глобальный DoD»; задачи добавляют только специфичные критерии.

## 4. Сквозные инварианты архитектуры (проверять в каждой задаче)

- **Ports & adapters** — ядро (`core/`) не зависит от реализаций; провайдеры живут в `adapters/` за портами.
- **Сменность только конфигом** — LLM/STT/CRM меняются через `base_url`/`model`/`api_key`/выбор адаптера,
  **без правок кода**. Дефолты MVP: `faster-whisper` (STT), `gpt-4o-mini` (LLM), `GoogleSheetsExporter` (CRM),
  оркестрация — LangGraph, checkpointer — Postgres.
- **Config-driven** — KPI/веса/провайдеры/язык берутся из `kpi.yaml`/`weights.yaml`/`providers`, не из кода.
- **Стабы перспективы** — `BadgeSource`/`TelephonySource` реализуют порт `AudioSource` как заглушки,
  **не ломающие ядро**.
- **Self-host LLM (vLLM/Qwen)** — целевой шаг **после MVP** (M9); подключается тем же портом `Analyzer`
  сменой конфига; код ядра не меняется.
- **ПДн** — `consent_flag` обязателен для боевых записей; доступ ограничен ролью (admin/viewer);
  `retention_until` + джоба чистки просроченных записей.

Дополнительно (из `docs/PLAN.md`):

- **Автономность ядра сначала** — M0–M3 собираются **без внешних API-ключей** (STT self-host, анализ на стабе);
  облачный LLM подключается на M4 за портом, но для CI/офлайн-разработки используется стаб-`Analyzer`.
- **Единый граф для всех источников** — источник лишь кладёт job; дальше один LangGraph-граф (`docs/PLAN.md §2.3`).
- **Структура каталогов** — строго по `docs/PLAN.md §2.2`; задачи ссылаются на неё в поле «Затрагивает».

## 6. Открытые вопросы и расхождения docs/PLAN.md ↔ ТЗ

> Спорные места помечены здесь и в соответствующих шардах как «открытый вопрос». Вопросы заказчику
> не задаются — решения зафиксированы по приоритету docs/PLAN.md, открытые места отмечены явно.

### 6.1 Расхождения docs/PLAN.md ↔ ТЗ (приоритет — docs/PLAN.md)

1. **CRM по умолчанию.**
   - ТЗ §2/§4.6: дефолт — **`Bitrix24Exporter`** (fallback — JSON/webhook).
   - docs/PLAN.md §1/§5 M8: дефолт MVP — **`GoogleSheetsExporter`** (бесплатно, виден результат без CRM-аккаунта);
     Bitrix24/webhook — опции/перспектива.
   - **Решение:** следуем docs/PLAN.md → дефолт `GoogleSheetsExporter`. Bitrix24 — отдельная задача-опция в M8.
     На M4 для сквозного пайплайна используется `JSONExporter` (так в docs/PLAN.md §5 M4).

2. **Где появляется экспорт первый раз.**
   - ТЗ ставит CRM-экспорт как отдельный блок §4.6.
   - docs/PLAN.md: на M4 экспорт = `JSONExporter` (для замыкания пайплайна), полноценный `GoogleSheetsExporter`
     и опции — только на M8. **Следуем docs/PLAN.md.**

3. **LLM-хостинг на MVP.**
   - ТЗ §6 даёт развилку «облако vs self-host» без жёсткого выбора.
   - docs/PLAN.md фиксирует: STT — self-host с самого старта; LLM — облако `gpt-4o-mini` на MVP, self-host
     vLLM/Qwen — **целевой шаг после MVP (M9)**. **Следуем docs/PLAN.md.**

4. **Скрипт: форматы файлов.**
   - ТЗ §4.9: txt/docx/markdown.
   - docs/PLAN.md явно форматы не перечисляет. **Решение:** в MVP принимаем txt/markdown как обязательные,
     docx — **открытый вопрос** (зависит от наличия парсера; вынесено в M6 как опциональная подзадача).

### 6.2 Открытые вопросы (из `docs/PLAN.md §7–8`, не блокируют план)

- **GPU под пилот** — на MVP нужен только под whisper; объём VRAM определит размер Qwen2.5 на M9. (M3, M9)
- **Bitrix24** — подтвердить целевую сущность и маппинг полей (дело/комментарий/поле сделки). (M8)
- **Retention-срок** — конкретное значение `retention_until` задаёт заказчик; в плане — конфигурируемый
  параметр + джоба удаления. (M1, M4)
- **Облачный LLM-провайдер и допустимость отправки транскриптов на пилоте** — на MVP допустимо с
  согласием/обезличиванием; целевое снятие риска — M9. (M4, M9)
- **Google-аккаунт/таблица** (сервисный аккаунт, доступ к Sheets) для `GoogleSheetsExporter`. (M8)
- **Диаризация** — ТЗ §4.2 допускает базовую через сегменты STT, без точного разделения голосов.
  **Решение:** в MVP только сегменты STT (speaker turns опционально), точная диаризация — перспектива. (M3)
- **docx-парсинг скриптов** — см. §6.1 п.4. (M6)
