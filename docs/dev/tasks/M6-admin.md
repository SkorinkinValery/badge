# M6 — Админка: менеджеры, скрипты, дневная сводка

> Этап `docs/PLAN.md §5 M6`. Базовые соглашения, TDD-цикл, слои тестов и глобальный DoD — см.
> [README.md](README.md) (§2–§4).

## Цель этапа

Админка (та же Next.js + Mantine, роль admin): CRUD менеджеров; загрузка и версионирование эталонных
скриптов; включение script-based-режима per-менеджер; дневная сводка по менеджеру (кол-во/длительность/
средний балл/% по KPI/нарушения, фильтры менеджер+дата).

## Входные предпосылки

- M5 завершён: auth, роли, UI-каркас, карточка.

## Выходной результат (DoD этапа)

- CRUD менеджеров (ФИО, должность, device_id, активность, default_script_id) — API + UI (admin).
- Загрузка скриптов (txt/markdown) с версионированием (`script_ver`), привязкой к KPI, выбором активного.
- Запись менеджера с активным скриптом автоматически идёт в script-based (связка с M4-T6).
- Дневная сводка: агрегаты + нарушения скрипта; фильтры менеджер+дата (диапазон — на вырост).

## Чек-лист задач

- [ ] M6-T1 — CRUD менеджеров — API
- [ ] M6-T2 — Загрузка + версионирование скриптов (`script`/`script_ver`) — API
- [ ] M6-T3 — Привязка активного скрипта к менеджеру → выбор script-based режима
- [ ] M6-T4 — Сервис дневной сводки (агрегаты + нарушения) + API
- [ ] M6-T5 — UI: менеджеры (CRUD)
- [ ] M6-T6 — UI: загрузка/версии скриптов
- [ ] M6-T7 — UI: дневная сводка (фильтры менеджер+дата)

### M6-T1: CRUD менеджеров — API

- **Цель / зачем:** Управление менеджерами (ТЗ §4.8) — привязка записей и скриптов.
- **Зависит от:** M5-T3, M1-T5
- **Затрагивает:** `app/api/managers.py`, `app/db/repositories/manager.py`.
- **TDD:**
  1. *Red* — `backend/tests/api/test_managers.py` — кейсы: create/list/get/update/delete менеджера (ФИО,
     должность, `device_id`, `активен`, `default_script_id?`); только admin; `device_id` уникален; деактивация

- **Слой тестов:** API.
- **Definition of Done:** глобальный DoD + операции под ролью admin; `default_script_id` опционален.
- **Acceptance / как проверить:** `pytest backend/tests/api/test_managers.py`.
- **Заметки по портам/конфигу:** менеджер — доменная сущность; привязка к записи (M2) и скрипту (M6-T3).

### M6-T2: Загрузка + версионирование скриптов — API

- **Цель / зачем:** Эталонные скрипты как reference для скоринга с историей версий (ТЗ §4.9, `docs/PLAN.md §3`).
- **Зависит от:** M5-T3, M1-T5
- **Затрагивает:** `app/api/scripts.py`, `app/db/repositories/script.py`, `app/services/scripts.py`.
- **TDD:**
  1. *Red* — `backend/tests/api/test_scripts.py` — кейсы: загрузка скрипта (txt/markdown) создаёт `script` +
     `script_ver` (версия, контент, привязка KPI); повторная загрузка создаёт **новую версию**, старые
     сохраняются (воспроизводимость); выбор активной версии; невалидный формат → 422.
  2. *Green* — приём текста/файла, парсинг txt/md, создание версии.
  3. *Refactor* — нормализация текста; diff-метка между версиями (опционально).
- **Слой тестов:** API.
- **Definition of Done:** глобальный DoD + версии неизменяемы; активная версия выбирается; форматы txt/markdown.
- **Acceptance / как проверить:** `pytest backend/tests/api/test_scripts.py`.
- **Заметки по портам/конфигу:** привязка KPI скрипта — через `kpi.yaml` id; не хардкод.
- **Открытый вопрос:** docx-парсинг (ТЗ §4.9) — опциональная подзадача; зависит от наличия парсера (см. README §6.1 п.4).

### M6-T3: Привязка активного скрипта → выбор script-based режима

- **Цель / зачем:** Связать наличие активного скрипта менеджера с автоматическим выбором режима анализа
  (ТЗ §4.4/§4.9) — замыкает M4-T6.
- **Зависит от:** M6-T1, M6-T2, M4-T6
- **Затрагивает:** `app/services/process.py` (выбор режима), `app/db/repositories/manager.py`.
- **TDD:**
  1. *Red* — `backend/tests/services/test_mode_selection.py` — кейсы: менеджер с активным скриптом → анализ в
     режиме `script` (промпт сверяет с эталоном, ищет нарушения); без скрипта → `baseline`; смена активной версии
     влияет на новые записи, старые ссылаются на свою `script_version_id`.
  2. *Green* — резолвер активного скрипта менеджера → передача в `Analyzer.analyze(script=...)`.
  3. *Refactor* — кэш активного скрипта; per-канал выбор (задел, ТЗ §4.9).
- **Слой тестов:** unit/интеграция (граф).
- **Definition of Done:** глобальный DoD + воспроизводимость: `analysis.script_version_id` фиксирует версию.
- **Acceptance / как проверить:** `pytest backend/tests/services/test_mode_selection.py`.
- **Заметки по портам/конфигу:** скрипт — контекст для `Analyzer` (ТЗ §7), не данные обучения; провайдер-агностично.

### M6-T4: Сервис дневной сводки + API

- **Цель / зачем:** Дневная сводка по менеджеру: агрегаты + нарушения (ТЗ §4.8) — ключевая ценность для руководителя.
- **Зависит от:** M6-T1, M4-T6
- **Затрагивает:** `app/services/daily_summary.py`, `app/api/admin.py`.
- **TDD:**
  1. *Red* — `backend/tests/services/test_daily_summary.py` + `backend/tests/api/test_admin_summary.py` —
     кейсы: за дату по менеджеру считаются кол-во разговоров, суммарная/средняя длительность, средний балл,
     разбивка по KPI (% выполнения каждого пункта), список нарушений скрипта, топ проблемных пунктов; фильтр
     менеджер+дата; пустой день → нули; диапазон дат (на вырост) поддержан схемой.
  2. *Green* — агрегирующие запросы + сервис; роутер.
  3. *Refactor* — вынести агрегаты в SQL; кэш на дату.
- **Слой тестов:** unit (агрегация) + API.
- **Definition of Done:** глобальный DoD + сводка под ролью (admin/viewer-руководитель); нарушения = KPI-пункты
  регламента со значением «нет» (ТЗ §4.5).
- **Acceptance / как проверить:** `pytest backend/tests/services/test_daily_summary.py backend/tests/api/test_admin_summary.py`.
- **Заметки по портам/конфигу:** % по KPI читается из доменного `Analysis`; провайдер-агностично.
