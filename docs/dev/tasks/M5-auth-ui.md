# M5 — Auth + минимальный UI

> Этап `docs/PLAN.md §5 M5`. Базовые соглашения, TDD-цикл, слои тестов и глобальный DoD — см.
> [README.md](README.md) (§2–§4).

## Цель этапа

Аутентификация (JWT OAuth2 password + argon2, роли admin/viewer) и минимальный UI (Next.js + Mantine):
список записей со статусами + карточка разговора (плеер + транскрипт + summary + KPI-таблица с цитатами +
балл) + ручная корректировка оценки. Доступ к записям ограничен ролью (ПДн).

## Входные предпосылки

- M4 завершён: сквозной пайплайн, API транскрипта/анализа, ручная корректировка.

## Выходной результат (DoD этапа)

- `POST /api/auth/login` выдаёт JWT; защищённые роуты требуют токен; роли admin/viewer разграничены.
- Доступ к записям/транскриптам/анализу ограничен ролью (ПДн, ТЗ §8/§4.8).
- UI: страница списка записей (статусы), карточка разговора (плеер по таймкодам, транскрипт, summary,
  KPI-таблица с цитатами, балл/вердикт), форма ручной корректировки.

## Чек-лист задач

- [ ] M5-T1 — Модель `user` + argon2-хэш + сидинг admin
- [ ] M5-T2 — `POST /api/auth/login` (OAuth2 password) → JWT
- [ ] M5-T3 — JWT-зависимость + ролевые guard'ы (admin/viewer) + ограничение доступа к записям
- [ ] M5-T4 — Каркас frontend (Next.js App Router + Mantine) + auth-флоу + API-клиент
- [ ] M5-T5 — Страница списка записей (статусы, фильтры) — UI
- [ ] M5-T6 — Карточка разговора (плеер + транскрипт + summary + KPI-таблица с цитатами + балл) — UI
- [ ] M5-T7 — Ручная корректировка оценки в карточке — UI

### M5-T1: Модель `user` + argon2 + сидинг admin

- **Цель / зачем:** Хранение пользователей с безопасным хэшем и стартовый admin (ТЗ §4.8, `docs/PLAN.md §3`).
- **Зависит от:** M1-T5
- **Затрагивает:** `app/db/models/user.py` (уже есть из M1-T5 — дополняется), `app/services/auth.py`,
  `app/db/migrations/<rev>_seed_admin.py` или CLI-сид.
- **TDD:**
  1. *Red* — `backend/tests/services/test_password.py` — кейсы: argon2 хэширует и верифицирует пароль;
     неверный пароль → false; роль ∈ {admin, viewer}; сид admin создаётся идемпотентно.
  2. *Green* — argon2-хэш/верификация; сидинг admin из env.
  3. *Refactor* — параметры argon2 в конфиг; CLI-команда `create-user`.
- **Слой тестов:** unit.
- **Definition of Done:** глобальный DoD + пароль admin — из env/секрета, не в коде; роли — Enum.
- **Acceptance / как проверить:** `pytest backend/tests/services/test_password.py`.
- **Заметки по портам/конфигу:** креды admin — из env (секрет), не из yaml.

### M5-T2: `POST /api/auth/login` → JWT

- **Цель / зачем:** Выдача токена по логину/паролю (ТЗ §4.8).
- **Зависит от:** M5-T1
- **Затрагивает:** `app/api/auth.py`, `app/services/auth.py`.
- **TDD:**
  1. *Red* — `backend/tests/api/test_auth.py` — кейсы: валидные креды → 200 + JWT (с `sub`/`role`/exp);
     неверные креды → 401; токен подписан и декодируется; истёкший токен невалиден.
  2. *Green* — OAuth2 password flow + выпуск JWT (HS/RS, секрет из конфига).
  3. *Refactor* — refresh-стратегия (опционально); вынести JWT-утилиты.
- **Слой тестов:** API.
- **Definition of Done:** глобальный DoD + секрет JWT из env; срок жизни токена конфигурируем.
- **Acceptance / как проверить:** `pytest backend/tests/api/test_auth.py`.
- **Заметки по портам/конфигу:** параметры JWT — в конфиге/env.

### M5-T3: JWT-зависимость + ролевые guard'ы + ограничение доступа к записям

- **Цель / зачем:** Защитить роуты и ограничить доступ к записям ролью — обязательное ПДн-требование (ТЗ §8).
- **Зависит от:** M5-T2, M2-T6, M3-T6, M4-T8
- **Затрагивает:** `app/api/deps.py` (`get_current_user`, `require_role`), применение к роутерам
  `recordings`/`transcript`/`analysis`.
- **TDD:**
  1. *Red* — `backend/tests/api/test_authz.py` — кейсы: без токена → 401; viewer видит записи (read-only),
     но не админ-операции; admin — всё; ручная корректировка (PATCH analysis) разрешена по роли; доступ к
     записям ограничен (viewer — просмотр, ПДн).
  2. *Green* — зависимости `get_current_user`/`require_role`; навесить на защищённые роуты.
  3. *Refactor* — единый декоратор/Depends для ролей; 403 vs 401 корректно.
- **Слой тестов:** API.
- **Definition of Done:** глобальный DoD + все роуты с боевыми записями под аутентификацией; доступ ограничен
  ролью (ПДн); ручная правка под нужной ролью.
- **Acceptance / как проверить:** `pytest backend/tests/api/test_authz.py`.
- **Заметки по портам/конфигу:** роли — простые admin/viewer (ТЗ §4.8), без сложного RBAC.

### M5-T4: Каркас frontend (Next.js + Mantine) + auth-флоу

- **Цель / зачем:** Поднять фронт с App Router, Mantine и авторизацией — основа UI и админки (`docs/PLAN.md §1`).
- **Зависит от:** M5-T2
- **Затрагивает:** `frontend/` (Next.js App Router), `frontend/lib/api.ts`, `frontend/app/(auth)/login`.
- **TDD:**
  1. *Red* — `frontend` component/e2e тесты (Vitest/Playwright) — кейсы: форма логина отправляет креды,
     хранит токен, редиректит; защищённые страницы недоступны без токена; разлогин чистит токен.
  2. *Green* — Next.js каркас + Mantine provider + API-клиент с прокидыванием JWT; страница логина.
  3. *Refactor* — единый fetch-wrapper (401→редирект); типы из OpenAPI-схемы бэкенда.
- **Слой тестов:** frontend unit/e2e (вне pytest; гоняется в CI отдельной джобой).
- **Definition of Done:** глобальный DoD + токен хранится безопасно; защита роутов; lint фронта в CI.
- **Acceptance / как проверить:** `npm test` / `npm run e2e` в `frontend/`.
- **Заметки по портам/конфигу:** базовый URL API — из env фронта.

### M5-T6: Карточка разговора — UI

- **Цель / зачем:** Главный экран ценности: плеер + транскрипт + summary + KPI-таблица с цитатами + балл
  (ТЗ §4.7).
- **Зависит от:** M5-T5, M3-T6, M4-T8
- **Затрагивает:** `frontend/app/recordings/[id]/page.tsx`, компоненты плеера/транскрипта/KPI-таблицы.
- **TDD:**
  1. *Red* — компонент-тесты — кейсы: плеер играет аудио (presigned URL) и переходит по таймкодам сегментов;
     транскрипт по сегментам; summary (3–7 пунктов); KPI-таблица с цитатами-доказательствами; балл + вердикт `+/~/-`;
     состояние «ещё обрабатывается»/«ошибка».
  2. *Green* — карточка с секциями, запросы transcript/analysis, плеер.
  3. *Refactor* — подсветка сегмента при воспроизведении; общий компонент KPI-строки.
- **Слой тестов:** frontend unit.
- **Definition of Done:** глобальный DoD + цитаты-доказательства видны на каждом KPI (ТЗ §4.4); таймкоды кликабельны.
- **Acceptance / как проверить:** ручной сценарий `docs/PLAN.md §6.2`; `npm test`.
- **Заметки по портам/конфигу:** UI отображает доменные `Transcript`/`Analysis`.

### M5-T7: Ручная корректировка оценки — UI

- **Цель / зачем:** Дать корректировать оценку для разметки/калибровки (ТЗ §4.7, `docs/PLAN.md §5 M5`).
- **Зависит от:** M5-T6, M4-T8
- **Затрагивает:** `frontend/app/recordings/[id]/` (форма правки).
- **TDD:**
  1. *Red* — компонент-тест — кейсы: правка значения KPI/балла отправляет `PATCH …/analysis`; авто-оценка
     сохраняется отдельно (видно «исходно/правка»); только разрешённая роль; ошибка сохранения отображается.
  2. *Green* — форма + мутирующий запрос + оптимистичный апдейт.
  3. *Refactor* — валидация значений по типу KPI (fact/scale).
- **Слой тестов:** frontend unit.
- **Definition of Done:** глобальный DoD + оригинальная авто-оценка не теряется (для eval M10); правка под ролью.
- **Acceptance / как проверить:** ручной сценарий правки; `npm test`.
- **Заметки по портам/конфигу:** правки идут в доменный `Analysis`, провайдер-агностично.
